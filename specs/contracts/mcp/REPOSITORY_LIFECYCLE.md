# Создание и индексирование репозиториев (MCP tools 0.6)

Нормативный сценарий добавления существующего каталога:

1. Агент вызывает `repository_index` с `{"repository_path": "/absolute/path/to/repository"}`.
   Это абсолютный путь существующего каталога на файловой системе MCP-сервера; UUID ещё
   не требуется. Список `repository_list` может быть пустым. Создавать или клонировать
   repository для этой операции не нужно.
2. MCP проверяет, что указанный каталог существует и является точным корнем Git repository,
   **до чтения DSL и проверки содержимого**. Вложенный каталог отклоняется без проверки
   содержимого родительского repository и без автоматической подмены пути.
   Собственный `.git` требуется только в конечном каталоге: это каталог Git metadata или
   обычный файл-ссылка Git worktree/separate git directory. Symlink `.git` отклоняется.
   У родителей `.git` может отсутствовать или принадлежать другому repository.
3. MCP читает `architecture.yaml` непосредственно в указанном каталоге. Необязательный
   `declaration_path` задаётся относительно этого же каталога; пути templates и entities
   всегда разрешаются относительно корня указанного repository, даже если декларация вложена.
   Текущий рабочий каталог сервера и ранее индексированные repositories не задают область проверки.
4. Только после успешной проверки содержимого MCP сохраняет канонический абсолютный путь
   **этого каталога** и UUID в индексе. Ошибка оставляет индекс без изменений. Агент сообщает
   ошибку проверки и не создаёт другой repository вместо указанного.
5. Агент берёт `result.repository_id` из ответа и передаёт его в `repository_describe`,
   `repository_open` и операции с сущностями. При нестандартном `declaration_path` он продолжает
   явно передавать тот же относительный путь декларации.

Этот сценарий должен быть доступен агенту через MCP server instructions и описание tool
`repository_index`, включая пример аргументов, отсутствие требования UUID и порядок проверки.

Нормативный сценарий создания нового repository:

1. `repository_create()` возвращает `phase=guide`: таблицу пресетов DSL, таблицу
   направленных связей примера, инструкции и полные примеры `architecture_yaml` + `templates`.
   Вызов не создаёт repository и не выбирает модель автоматически.
2. Агент составляет декларацию и шаблоны под запрос пользователя, затем вызывает тот же
   инструмент с `target_path`, `architecture_yaml` и `templates`. Все три аргумента обязательны
   вместе. Templates — объект `repository-relative POSIX path -> UTF-8 content`, содержащий
   ровно объявленные шаблоны. `declaration_source` больше не является публичным аргументом.
3. MCP проверяет DSL, пути, форматы и связи шаблонов до размещения результата в target.
   Создаёт `architecture.yaml`, объявленные шаблоны и каталоги `path.match=exact`.
   Regex не превращается в выдуманный путь: соответствующие каталоги создаёт `entity_create`
   по явно переданному пути экземпляра. Git инициализируется с `initial_branch=main`, если
   агент не указал другую ветку. Commit, remote и push не создаются.
4. Успех (`phase=created`) возвращает UUID `repository_id` и абсолютный `repository_root`.
   Невалидный bundle не оставляет target или запись индекса. Существующий target не заменяется.

`target_path` создания/клонирования и `repository_path` индексации должны быть
абсолютными. Родитель target должен существовать. Repository root не может быть symlink.
Unicode-символы и пробелы в именах каталогов сохраняются, включая повторяющиеся пробелы
и пробелы в начале или конце имени; они не обрезаются при определении Git root и индексации.
Корень сравнивается по идентичности каталога файловой системы, а не по строковому совпадению.
Если разные Unicode-представления (NFC/NFD) или регистр обозначают один и тот же каталог
на данной файловой системе, index/reindex сохраняют один UUID. Разные физические каталоги
не объединяются путём приведения строк к нижнему регистру или Unicode-нормализации.
Новые записи используют абсолютный путь корня, возвращённый Git. Ранее сохранённые варианты
пути того же каталога сохраняют UUID и остаются доступными после перезапуска.
Унаследованные переменные расположения Git (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`,
`GIT_INDEX_FILE`, object directory и discovery overrides) не перенаправляют операции:
они удаляются из окружения дочерних Git-процессов при создании, индексации и работе с repository.
Пути в DSL не могут обращаться к `.git`, содержать traversal или Windows drive prefixes.
Настройки workspace, repository path и env-file больше не читаются из environment или `.env`.

Индекс находится в `~/.config/arch-repo-mcp/repositories.json` и создаётся при первом обращении
к индексу (в том числе при старте сервера). Формат:

```json
{"version": 1, "repositories": [{"repository_id": "UUID", "repository_path": "/absolute/path"}]}
```

UUID уникальны, пути канонические и уникальны. Запись атомарная с блокировкой между процессами.
Повреждённый индекс вызывает `INVALID_REPOSITORY` и не перезаписывается. Ошибка доступа
возвращает `PERMISSION_DENIED`. Если запись индекса после создания/клонирования не удалась,
созданный валидный каталог сохраняется; ошибка содержит `repository_path` и указание выполнить
`repository_reindex`. Потеря пользовательских файлов ради отката индекса недопустима.

`repository_list()` возвращает `index_path` и записи индекса, включая устаревшие записи;
не сканирует каталоги и не выбирает repository неявно.

Все операции над индексированным repository принимают обязательный `repository_id` вместо
`repository_path`. Некорректный UUID даёт `VALIDATION_ERROR`, отсутствующая запись — `NOT_FOUND`.
UUID не интерпретируется как путь. Исчезнувший путь не переназначается; symlink или путь,
ставший вложенным каталогом другого Git repository, отклоняется. Git inspection остаётся
доступным при невалидном DSL для диагностики.

`repository_unindex(repository_id)` удаляет только запись индекса, даже если каталог уже
отсутствует или невалиден. Физические файлы и Git не изменяются. Повторное удаление — `NOT_FOUND`.

`repository_index(repository_path, declaration_path="architecture.yaml")` проверяет точный
Git root и выполняет полную DSL/repository validation, затем добавляет запись. Для уже
индексированного пути возвращается прежний UUID. После удаления записи или переноса каталога
выдаётся новый UUID; старую запись после переноса удаляют явно. Невалидный repository не
добавляется. Инструмент не изменяет файлы repository и не обращается к сети.

Проверка содержимого включает декларацию DSL, шаблоны, форматы сущностей, file matching,
пути и связи согласно DSL. Она выполняется при каждом вызове, включая уже индексированный
путь; ошибка проверки не изменяет существующие записи индекса. Успешный ответ содержит
`repository_id` (UUID) и `repository_path` (канонический абсолютный путь). UUID хранится
в пользовательском индексе, а не в файлах repository, и сохраняется между запусками сервера.

`repository_reindex` сохранён как совместимый инструмент с теми же аргументами, результатом
и поведением, что и `repository_index`.

`repository_clone` после успешной проверки также индексирует результат и возвращает UUID.
`repository_open` принимает UUID и проверяет существующий repository, не выполняя индексацию.
Необязательный `declaration_path` существующих операций сохраняется для репозиториев с
нестандартным именем декларации; для них агент должен явно передавать его при каждом вызове.
