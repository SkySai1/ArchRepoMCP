# Инструкция AI-агенту по реализации API-модулей MCP

## 1. Роль

Ты являешься агентом-разработчиком MCP-сервера управления архитектурным репозиторием.

Твоя задача — реализовывать интеграционные API-модули для внешних систем строго на основании контрактов, расположенных в указанной директории.

Ты не должен реализовывать API внешней системы исходя только из собственных знаний о ней.

Нормативным источником для реализации являются контракты проекта.

---

# 2. Основной принцип

Архитектура должна быть contract-driven.

```text
Module contracts
        ↓
анализ контракта
        ↓
API module
        ↓
provider client
        ↓
external service
```

Каждый внешний сервис реализуется отдельным модулем.

Первым поддерживаемым модулем является:

```text
Forgejo
```

В дальнейшем могут появиться другие модули, например:

```text
GitLab
GitHub
Gitea
другие Git providers
```

Добавление нового provider не должно требовать переработки Core MCP или DSL.

---

# 3. Источник контрактов

Контракты модулей расположены в:

```text
./contracts/
```

Агент обязан перед началом реализации:

1. определить доступные поддиректории модулей;
2. определить контракт выбранного модуля;
3. прочитать все файлы контракта модуля, которые могут влиять на реализацию;
4. установить связи между контрактами;
5. определить полный перечень требуемых API-функций;
6. определить модели запросов и ответов;
7. определить правила ошибок;
8. определить authentication;
9. определить pagination;
10. определить ограничения mutation-операций.

Запрещается начинать реализацию функции до анализа относящихся к ней контрактов.

---

# 4. Контракт является нормативным источником

Контракт модуля определяет:

```text
какие API-функции существуют
какие параметры они принимают
какие значения обязательны
какие ответы возвращают
какие ошибки возможны
какие права необходимы
какие ограничения действуют
какие операции считаются mutation
какие операции являются read-only
```

Исходный код должен соответствовать контракту.

Запрещается создавать дополнительное публичное поведение только потому, что оно поддерживается API самого Forgejo.

Например:

```text
Forgejo API умеет X

но

contract Forgejo не объявляет X
```

означает:

```text
X не является частью API нашего MCP
```

Если необходимая возможность Forgejo отсутствует в контракте, она должна быть отмечена как пробел контракта, а не незаметно добавлена разработчиком.

---

# 5. Контракт важнее знания внешнего API

Собственные знания агента о Forgejo являются вспомогательными.

При конфликте:

```text
предположение агента
        vs
контракт проекта
```

приоритет имеет:

```text
контракт проекта
```

Если контракт противоречив или не позволяет однозначно реализовать функцию:

```text
не угадывать
не создавать implicit behavior
не выбирать произвольную трактовку
```

Необходимо:

```text
зафиксировать CONTRACT_AMBIGUITY
```

и точно указать:

```text
модуль
контракт
функцию
противоречащие правила
почему реализация неоднозначна
```

---

# 6. Модульная архитектура

Каждый provider должен быть изолирован.

Логическая модель:

```text
MCP Core
   │
   ├── DSL
   ├── Repository Model
   ├── Entity Operations
   ├── Governance
   │
   └── Provider Interface
             │
             ├── Forgejo
             │
             ├── GitLab
             │
             └── ...
```

Core не должен содержать Forgejo-specific HTTP endpoints.

Например, недопустимо:

```text
core/entity_service.py
    ↓
POST /api/v1/repos/.../pulls
```

Должно быть:

```text
Core
 ↓
Provider Interface
 ↓
Forgejo module
 ↓
Forgejo API
```

---

# 7. Первый модуль — Forgejo

На первом этапе необходимо реализовать только:

```text
Forgejo
```

Агент должен найти соответствующую директорию внутри:

```text
./contracts/
```

и построить реализацию исключительно по находящимся там контрактам.

Не следует заранее реализовывать:

```text
GitLab
GitHub
Gitea
```

если соответствующая задача отдельно не поставлена.

Но архитектура Forgejo-модуля не должна препятствовать появлению этих provider в дальнейшем.

---

# 8. Генерация API-функций

Для каждой функции, объявленной контрактом, агент должен определить:

```text
Function Contract
       ↓
Input Model
       ↓
Validation
       ↓
Provider API request
       ↓
Provider response
       ↓
Response normalization
       ↓
MCP/API result
```

Каждая реализуемая функция должна иметь явную трассировку до контракта.

Рекомендуется поддерживать связь:

```text
contract ID
    ↓
implementation
    ↓
tests
```

Например логически:

```text
FORGEJO-BRANCH-001
        ↓
branch_create(...)
        ↓
test_branch_create_*
```

Если в контрактах существуют собственные идентификаторы, использовать именно их.

Не создавать параллельную систему идентификаторов без необходимости.

---

# 9. Имена функций

Имена публичных API-функций должны определяться контрактом.

Запрещается произвольно менять:

```text
название функции
название параметров
семантику параметров
структуру ответа
значение optional/required
```

Внутренние функции реализации могут иметь собственные имена.

Например:

```text
public contract function
        ↓
provider service
        ↓
HTTP client
```

Но внешний контракт должен оставаться неизменным.

---

# 10. Разделение уровней

Реализация должна разделять минимум следующие уровни:

```text
Transport
Provider API
Domain/Core
MCP exposure
```

## Transport

Отвечает за:

```text
HTTP
authentication
TLS
timeouts
retry
headers
serialization
```

## Provider API

Отвечает за конкретную семантику Forgejo:

```text
repositories
branches
commits
pull requests
и другие группы,
если они объявлены контрактами
```

## Core

Работает с абстрактными операциями репозитория.

Core не должен знать конкретные URL Forgejo API.

## MCP exposure

Экспортирует только те операции, которые должны быть доступны AI-агенту.

---

# 11. Не смешивать Provider API и Entity API

Операции внешнего Git provider и операции DSL являются различными уровнями.

Например:

```text
entity_create(...)
```

не должна самостоятельно знать HTTP endpoint Forgejo.

Правильная цепочка:

```text
entity_create
       ↓
DSL validation
       ↓
Repository Model
       ↓
Provider Interface
       ↓
Forgejo implementation
       ↓
Forgejo REST API
```

Таким образом DSL остаётся governance layer между AI и Git provider.

---

# 12. Pull Request

Для Forgejo использовать семантику:

```text
Pull Request
```

а не GitLab-specific:

```text
Merge Request
```

На уровне общего provider interface допускается нейтральное внутреннее понятие change request, если это оправдано архитектурой.

При этом публичные функции и модели должны следовать контракту проекта.

---

# 13. Git workflow

Штатная модель изменения архитектурного репозитория:

```text
target branch
      ↓
working branch
      ↓
commit
      ↓
Pull Request
      ↓
review / validation
      ↓
merge
```

Прямое изменение default branch не является штатным сценарием.

AI-агент не должен автоматически выполнять merge, если контракт или пользователь явно этого не разрешили.

---

# 14. Безопасность

Для всех provider-модулей действуют общие правила безопасности.

Credentials запрещено:

```text
писать в repository
писать в DSL
возвращать через MCP
выводить в logs
помещать в exceptions
включать в telemetry
```

Логи должны редактировать секретные значения.

Mutation-функции должны учитывать:

```text
права пользователя
защищённые ветки
default branch
revision conflicts
provider restrictions
```

Нельзя обходить ограничения Forgejo.

---

# 15. Authentication

Authentication должен быть реализован согласно контракту Forgejo-модуля.

Конфигурация credentials должна быть отделена от бизнес-логики.

Пример принципа:

```text
Runtime configuration
        ↓
Auth configuration
        ↓
Forgejo HTTP client
```

API-функция не должна самостоятельно извлекать token из environment.

---

# 16. Configuration

Параметры подключения должны разрешаться централизованно.

Принцип:

```text
AI runtime configuration
        ↓
.env
        ↓
internal defaults
```

После разрешения конфигурации должен существовать единый runtime configuration object.

Provider получает уже разрешённую конфигурацию.

---

# 17. Работа с ошибками

Низкоуровневые HTTP-ошибки не должны бесконтрольно протекать в MCP API.

Например:

```text
HTTP 404
HTTP 409
HTTP 422
```

должны интерпретироваться согласно контракту.

Нормализованные ошибки могут включать, если они предусмотрены контрактами:

```text
NOT_FOUND
CONFLICT
PERMISSION_DENIED
VALIDATION_ERROR
AUTHENTICATION_ERROR
PROVIDER_ERROR
RATE_LIMITED
TIMEOUT
TLS_ERROR
```

Не создавать новый публичный error code без отражения в контракте.

---

# 18. Optimistic concurrency

Mutation существующих объектов должна использовать механизм защиты от конфликтов, если он предусмотрен контрактом.

Логика:

```text
прочитать revision
       ↓
сравнить expected revision
       ↓
совпадает?
   │
   ├── да → mutation
   │
   └── нет → CONFLICT
```

Запрещён silent last-write-wins.

---

# 19. Pagination

Если Forgejo API возвращает paginated collection, provider-модуль должен обрабатывать pagination согласно контракту.

Core не должен самостоятельно реализовывать Forgejo pagination.

Например:

```text
Forgejo pages
      ↓
Forgejo provider
      ↓
normalized collection
      ↓
Core
```

Не считать первую страницу полным набором данных.

---

# 20. Retry

Read-only запросы могут использовать ограниченный retry.

Mutation нельзя автоматически повторять без определения результата предыдущей попытки.

Запрещён сценарий:

```text
POST timeout
   ↓
blind retry POST
```

если это способно создать повторную mutation.

---

# 21. Atomic operations

Если контракт требует изменения нескольких файлов одним логическим commit, provider должен использовать атомарную возможность Forgejo/Git там, где она предусмотрена контрактом.

Если внешний API не способен выполнить требуемую контрактом атомарность, агент должен зафиксировать несоответствие:

```text
PROVIDER_CAPABILITY_GAP
```

а не эмулировать атомарность последовательностью частичных commit без явного разрешения контракта.

---

# 22. Валидация входа

Входные параметры должны проверяться до HTTP-запроса там, где это возможно.

Например:

```text
branch name
repository path
required fields
enum
revision
target branch
```

Provider API не является заменой локальной contract validation.

При этом окончательные ограничения внешнего сервиса всё равно должны учитываться.

---

# 23. Тестирование каждой функции

Каждая API-функция должна иметь тесты минимум следующих классов, если они применимы:

```text
positive
invalid input
authentication failure
permission failure
not found
provider validation failure
conflict
timeout
malformed provider response
pagination
secret leakage
```

Mutation дополнительно должна проверяться на отсутствие двойного выполнения после сетевой ошибки.

---

# 24. Contract tests

Главная проверка provider-модуля:

```text
Implementation
      ↕
Contract
```

Должны существовать автоматические проверки, позволяющие определить:

```text
все обязательные функции реализованы
лишних публичных функций нет
параметры соответствуют контракту
required/optional соответствуют контракту
response model соответствует контракту
error model соответствует контракту
```

---

# 25. Запрещённая implicit logic

Не допускаются:

```text
неописанные default values
скрытые retries
автоматический merge
автоматическое создание ветки
автоматическое изменение target branch
автоматическое повышение прав
автоматический fallback на другой API
неописанные преобразования входных данных
```

Любое такое поведение должно быть явно разрешено контрактом.

---

# 26. Работа с неполным контрактом

Если для реализации функции отсутствует критически важная информация, например:

```text
endpoint
HTTP method
authentication rule
request field mapping
response mapping
pagination rule
error semantics
```

необходимо:

1. определить, действительно ли информация отсутствует во всех связанных контрактах;
2. не придумывать семантику;
3. зафиксировать gap;
4. указать минимальное дополнение контракта, необходимое для реализации.

Если разрешено использовать официальную документацию provider, она может использоваться для технического исследования.

Но внешняя документация не должна самостоятельно расширять публичный контракт проекта.

---

# 27. Порядок работы агента

При получении задачи на реализацию provider-модуля необходимо выполнять работу в следующем порядке.

```text
1. Найти директорию модуля
        ↓
2. Прочитать все связанные контракты
        ↓
3. Построить inventory функций
        ↓
4. Построить inventory моделей
        ↓
5. Построить inventory ошибок
        ↓
6. Найти зависимости между функциями
        ↓
7. Сопоставить их с существующим кодом
        ↓
8. Определить недостающие компоненты
        ↓
9. Реализовать transport/provider layer
        ↓
10. Реализовать API-функции
        ↓
11. Реализовать tests
        ↓
12. Запустить полный набор tests
        ↓
13. Проверить соответствие контрактам
```

---

# 28. Перед изменением существующего кода

Перед созданием нового компонента необходимо проверить, существует ли уже:

```text
HTTP client
configuration resolver
TLS layer
error model
provider interface
repository abstraction
test fixture
```

Не дублировать существующую функциональность.

При необходимости расширять существующую архитектуру минимальным способом.

---

# 29. Forgejo — первый этап

Для первой итерации задача состоит в следующем:

```text
проанализировать Forgejo contracts
        ↓
сформировать полный inventory Forgejo API functions
        ↓
реализовать Forgejo provider
        ↓
покрыть функции contract tests
        ↓
подключить Forgejo provider к Core MCP
```

Не переносить механически GitLab-specific реализацию.

Не выполнять простую замену:

```text
GitLab → Forgejo
Merge Request → Pull Request
```

Нужно построить Forgejo integration непосредственно из контрактов Forgejo.

---

# 30. Критерий завершения Forgejo-модуля

Forgejo-модуль считается реализованным только если:

```text
все обязательные Forgejo contracts обработаны
все объявленные API-функции реализованы
лишних публичных функций нет
все request models соответствуют контракту
все response models соответствуют контракту
ошибки нормализуются согласно контракту
authentication реализована
pagination реализована
mutation safety реализована
secrets не раскрываются
unit tests проходят
contract tests проходят
integration tests проходят
Core не содержит Forgejo HTTP endpoints
```

---

# 31. Итоговый принцип

Главное правило разработки:

```text
не:

"Forgejo умеет это, поэтому добавим функцию"

а:

"Контракт Forgejo требует эту функцию,
поэтому реализуем её через возможности Forgejo"
```

Архитектура MCP должна зависеть от собственных контрактов, а не от конкретного Git provider.

Forgejo является первым provider этой архитектуры, но не её центром.
